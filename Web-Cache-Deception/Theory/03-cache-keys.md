# Cache Keys

## Overview

A cache key is the value generated by a web cache from elements of an HTTP request.

The cache uses this key to determine whether a request matches a previously cached response.

---

# Basic Concept

When a request reaches the cache:

```text

     ↓

    ┌───┴───┐
   YES      NO

    ▼        ▼

  Hit      Server
What Makes Up a Cache Key?

The exact cache key depends on the cache implementation.

Typically, it includes:

URL Path
Query Parameters

It can also include other request elements such as:

Headers
Content-Type

The cache therefore decides which parts of the request are relevant when determining whether two requests should be considered equivalent.

Example

Consider:

GET /static/app.js

The cache generates a cache key based on the relevant parts of this request.

If another request produces the same cache key:

GET /static/app.js

the cache considers the requests equivalent and may return the stored response.

Cache Key Match
Request A
    ↓
Cache Key A
    │
    │ matches
    ▼
Cache Key B
    ↑
    │
Request B

If the cache key matches an existing cached response:

Request
  ↓
Matching Cache Key
  ↓
Cached Response

The origin server does not need to process the request again.

Different Cache Keys

Consider:

/request?user=1
/request?user=2

If query parameters are included in the cache key, these requests will normally produce different cache keys.

/request?user=1
        ↓
Cache Key A

/request?user=2
        ↓
Cache Key B

Therefore, they are treated as different cache entries.

Query Parameters

Because query parameters are typically included in the cache key, adding or changing a query parameter can create a different cache key.

Example:

/my-account?cb=1
/my-account?cb=2
/my-account?cb=3

Each request can produce a different cache key.

This is useful during security testing.

Cache Busters

A cachebuster is a changing query parameter used to ensure that each test request has a unique cache key.

Example:

?cb=001
?cb=002
?cb=003
Why Cachebusters Matter

Without a cachebuster, an earlier cached response can affect the result of a later test.

For example:

Test 1
   ↓
Response cached
   ↓
Test 2
   ↓
Existing cached response
   ↓
Misleading result

Using a unique cache key helps isolate each test:

Test 1 → ?cb=001
Test 2 → ?cb=002
Test 3 → ?cb=003
Burp Suite

The source material recommends using the Param Miner extension to automate dynamic cachebusters.

In Param Miner:

Param Miner
    ↓
Settings
    ↓
Add dynamic cachebuster

Burp then adds a unique query string to requests.

The generated query strings can be viewed in the Logger tab.

Cache Key and Web Cache Deception

Cache keys are important because Web Cache Deception depends on how the cache identifies requests.

The attacker wants to create a request where:

Origin Server
      ↓
Interprets request as sensitive dynamic resource

while:

Cache Server
      ↓
Treats request as a cacheable resource

The cache then stores the origin response under the cache key.

Example

Suppose the attacker discovers:

/my-account/abc.js

The origin interprets the request as:

/my-account

and returns sensitive account information.

The cache interprets the full path as:

/my-account/abc.js

and applies a .js cache rule.

The cached response is therefore associated with the cache key for:

/my-account/abc.js
Attack Flow
Victim
  ↓
/my-account/wcd.js
  ↓
Cache
  ↓
Cache Miss
  ↓
Origin
  ↓
Origin interprets as /my-account
  ↓
Sensitive Response
  ↓
Cache stores response
  ↓
Attacker requests same URL
  ↓
Cache Hit
  ↓
Sensitive Response
Cache Key vs Cache Rule

These concepts should not be confused.

Cache Key

Determines:

Which requests are considered equivalent?

Example:

/path/resource.js?x=1
Cache Rule

Determines:

Which responses should be stored?

Example:

*.js → cache
Why Both Matter

A Web Cache Deception vulnerability generally requires both:

Cache Key Behavior
        +
Cache Rule Behavior
        +
Origin/Cache Interpretation Difference

For example:

Origin
  ↓
Sensitive Dynamic Response

Cache Rule
  ↓
.js is cacheable

Cache Key
  ↓
Stores response under /my-account/wcd.js
Cache Key Testing

When testing an application, determine:

☐ Is the URL path part of the cache key?
☐ Are query parameters part of the cache key?
☐ Are headers part of the cache key?
☐ Does Content-Type affect the cache key?
☐ Does changing a parameter create a new cache entry?

The exact behavior depends on the cache implementation.

Cache Key Comparison

Example:

Request A:
GET /profile/wcd.js?cb=1

Request B:
GET /profile/wcd.js?cb=2

If the query parameter is part of the cache key:

Cache Key A ≠ Cache Key B

Therefore, they should not normally share the same cached response.

Testing Cache Behavior

A useful workflow is:

Send Request
     ↓
Observe X-Cache
     ↓
Change Cache Key
     ↓
Send Again
     ↓
Compare Result

For example:

X-Cache: miss

followed by the same request:

X-Cache: hit

can demonstrate that a response was cached.

Important Limitation

A cachebuster changes the cache key.

Therefore, it should be used carefully when confirming whether a particular malicious URL is cached.

For example:

Initial Test:
 /my-account/wcd.js?cb=1

Victim:
 /my-account/wcd.js

These may represent different cache keys.

For a final exploit demonstration, the attacker and victim need to access the same cache key while avoiding reuse of an earlier test response.

Cache Key Testing Workflow
Identify Dynamic Endpoint
        ↓
Add Cachebuster
        ↓
Establish Clean Baseline
        ↓
Modify URL
        ↓
Observe Cache Behavior
        ↓
Change Cachebuster
        ↓
Repeat Test
        ↓
Compare Cache Responses
Key Takeaways
A cache key identifies requests that the cache considers equivalent.
URL paths and query parameters are typically part of the cache key.
Headers and Content-Type may also influence the key depending on the implementation.
Matching cache keys can result in a cached response being served.
Cachebusters create unique cache keys and help prevent previous cached responses from affecting testing.
Cache keys determine which requests share a cache entry.
Cache rules determine which responses are eligible for caching.
Web Cache Deception relies on understanding both cache keys and cache rules.
