# Detecting Cached Responses

## Overview

When testing Web Cache Deception, it is important to determine whether a response was actually served from the cache.

A response being cacheable does not necessarily mean that it was cached.

The source material recommends examining:

- Response headers
- Response times
- Repeated requests

---

# Why Detection Matters

A Web Cache Deception attack depends on the sensitive response being stored by the cache.

Therefore, you need to establish:

```text
Origin Response
      ↓
Cache Stores Response
      ↓
Same Request
      ↓
Cache Serves Stored Response

Without confirming this behavior, a suspected WCD issue is not fully demonstrated.

1. X-Cache Header

The X-Cache response header can provide information about whether a response was served from the cache.

Common values include:

X-Cache: hit
X-Cache: miss
X-Cache: dynamic
X-Cache: refresh
X-Cache: hit

Example:

X-Cache: hit

This indicates that the response was served from the cache.

Flow:

Request
   ↓
Cache
   ↓
Matching Cached Response
   ↓
X-Cache: hit
   ↓
Response
X-Cache: miss

Example:

X-Cache: miss

This indicates that the cache did not contain a response matching the request's cache key.

The request was therefore fetched from the origin server.

In many cases, the resulting response is then cached.

To verify this, send the same request again.

First Request
     ↓
X-Cache: miss
     ↓
Origin Server
     ↓
Response
     ↓
Potentially Cached

Second Request
     ↓
X-Cache: hit
     ↓
Cached Response
X-Cache: dynamic

Example:

X-Cache: dynamic

This generally indicates that the content was dynamically generated by the origin server.

It generally means that the response is not considered suitable for caching.

X-Cache: refresh

Example:

X-Cache: refresh

This indicates that the cached content was outdated and needed to be refreshed or revalidated.

2. Cache-Control

Another useful response header is:

Cache-Control

For example:

Cache-Control: public, max-age=30

A directive such as:

public

combined with:

max-age > 0

can indicate that the resource is cacheable.

Cache-Control Is Not Proof

A cacheable response is not necessarily an actually cached response.

For example:

Cache-Control: public, max-age=30

suggests that caching is permitted.

However, the cache may override this behavior.

Therefore:

Cache-Control
      ↓
Indication of Cacheability

is different from:

X-Cache: hit
      ↓
Evidence of Cached Response
3. Response Timing

Response time can also provide evidence of caching.

For example:

Request 1 → 800 ms
Request 2 → 80 ms

A significant reduction in response time may indicate that the second response was served from the cache.

Conceptually:

Cache Miss
   ↓
Origin Processing
   ↓
Slower Response

Cache Hit
   ↓
Stored Response
   ↓
Faster Response
Timing Is Supporting Evidence

Response timing alone should not be treated as definitive proof.

Network conditions and server load can also affect response times.

Therefore, combine timing with:

X-Cache
Cache-Control
Repeated Requests
Response Comparison
4. Repeated Request Method

A simple way to investigate caching is to send the same request more than once.

First Request
GET /resource

Possible response:

X-Cache: miss
Second Request
GET /resource

Possible response:

X-Cache: hit

This sequence provides strong evidence that the response was cached.

5. Use a Cachebuster During Testing

When testing different URLs, use a unique cachebuster so that previous cache entries do not interfere with the result.

Example:

/resource?cb=001
/resource?cb=002
/resource?cb=003

Each request can produce a different cache key.

Cachebuster Workflow
Generate Unique Cache Key
          ↓
Send Request
          ↓
Observe Response
          ↓
Record X-Cache
          ↓
Change Cachebuster
          ↓
Repeat
          ↓
Compare Results

Param Miner can automate dynamic cachebusters.

6. Compare Response Bodies

When investigating a possible cache issue, compare:

Response 1
Response 2

Look for:

Same sensitive data
Same response body
Same relevant headers
Different X-Cache status

For example:

Request 1
X-Cache: miss
Response: Sensitive Account Data

Request 2
X-Cache: hit
Response: Same Sensitive Account Data

This provides useful evidence that the sensitive response was stored and subsequently served from the cache.

Example Detection

Suppose you test:

/my-account/abc.js

First response:

X-Cache: miss

The response contains:

Sensitive Account Information

Send the same request again.

Second response:

X-Cache: hit

and the response still contains:

Sensitive Account Information

Detection Indicators
Indicator	Meaning
X-Cache: hit	Response served from cache
X-Cache: miss	No matching cached response; fetched from origin
X-Cache: dynamic	Dynamically generated response; generally not suitable for caching
X-Cache: refresh	Cached content refreshed/revalidated
Cache-Control: public	Suggests response may be cacheable
max-age > 0	Suggests a caching lifetime

Important Distinction

Keep these concepts separate:

Cacheable
   ≠
Actually Cached

and:

Cached
   ≠
Vulnerable

A Web Cache Deception vulnerability requires the cached response to contain sensitive content in a way that creates unauthorized access.

Key Takeaways
X-Cache is one of the most useful indicators of cache behavior.
X-Cache: hit indicates that the response was served from the cache.
X-Cache: miss indicates that the cache did not have a matching response and the request was fetched from the origin.
X-Cache: dynamic generally indicates dynamically generated content that is not suitable for caching.
X-Cache: refresh indicates that cached content needed to be refreshed or revalidated.
Cache-Control can suggest cacheability but does not prove that a response was actually cached.
A significant response-time difference can provide additional evidence.
Repeating a request and comparing cache indicators is an effective way to confirm caching.
